# GitHub-Based Research Management Reference Architecture

**Phase 6 deliverable** (roadmap step 6 of 12) · Answers **RQ3** (constructive part)
**Artifacts (this directory):** `architecture_components.csv` (15 components), `workflows.csv` (7 workflows), `lifecycle_model.csv` (12 stages)
**Built on:** the Phase 5 coverage assessment (`framework/mapping/`) · **Decisions:** `docs/DECISION_LOG.md` D12

---

## 1. Concept

The architecture organises GitHub's Direct- and Partial-support capabilities (Phase 5) into a small set of named components, and specifies the **conventions** that turn generic features into research-usable support for the requirements GitHub covers only partially (RM1, RM2, RM5, RM10).

Design stance, unchanged from `docs/RESEARCH_DESIGN.md`:

> GitHub is a **central coordination and traceability layer**, not a container for every research activity.

Large datasets, computational environments, DOIs/preservation and institutional governance remain **outside** GitHub and are linked by reference (§7).

## 3. Components

Full detail in `architecture_components.csv`. Each row is *a thing you configure once in GitHub*, its GitHub basis, the convention (if any) that makes it research-usable, the requirements it serves, and its traceability role.

| ID | Component | GitHub basis | Serves |
|---|---|---|---|
| A1 | Research Plan | Project + 'Research phase'/iteration fields + roadmap view + milestones + pinned roadmap issue | RM1, RM3 |
| A2 | Activity Tracker | Issues-as-tasks (forms, activity labels, sub-issues, assignees) on the Project board | RM3, RM9 |
| A3 | Question Register | one issue per RQ ('RQ-n', label/Issue Type) + pinned index | RM2 |
| A4 | Discussion Space | Discussions (Q&A / Ideas / Poll) + mark-as-answer | RM7, RM5 |
| B1 | Documentation Set | `/docs` Markdown + folder READMEs + optional Pages | RM4, RM11 |
| B2 | Decision Log | `DECISION_LOG.md` + 'decision' issue template | RM5 |
| B3 | **Linkage Discipline** | cross-references + closing keywords + timeline | RM10, RM2, RM5 |
| B4 | Change History | Git commits (signed, co-authored) + tags | RM8, RM10 |
| C1 | Artifact Workspace | repo structure + LFS + external links | RM9, RM4 |
| C2 | Review Workflow | branches + PRs + reviews + CODEOWNERS + PR checklist | RM6, RM5, RM12 |
| C3 | Automation Suite | Actions (validation, repro matrix, packaging) + Dependabot | RM13, RM12, RM11 |
| D1 | Release Process | tagged Releases + autogenerated notes + CITATION.cff | RM14, RM8 |
| D2 | Archival Bridge | GitHub–Zenodo webhook + ORCID | RM14 |
| D3 | Governance Setup | roles/teams + visibility policy + CONTRIBUTING + audit log | RM15, RM6, RM11 |
| X1 | Transparency Surface | public visibility + Pages summary + Insights | RM11 |

**B3 Linkage Discipline is the keystone.** It is not a feature but a mandatory practice; without it the Record and Coordination layers do not connect and RM10 collapses to Limited.

## 4. Conventions that lift partial support

Phase 5 scored four requirements below Direct because their support rests on convention. The architecture makes those conventions explicit and mandatory:

| Requirement | Phase 5 | Lifting convention (component) |
|---|---|---|
| RM1 planning (Partial) | — | **Phased-plan convention** (A1): the 'Research phase' field uses the fixed lifecycle vocabulary; the roadmap issue is the versioned plan-of-record. |
| RM2 research-question mgmt (Limited) | — | **Question Register convention** (A3) + **Linkage discipline** (B3): one issue per RQ, fixed title, pinned index; every method/analysis issue and PR references its RQ; reformulations are timeline comments. |
| RM5 decision traceability (Partial) | — | **Decision-record convention** (B2): every significant decision gets a `Dn` entry *and* a 'decision' issue cross-referencing affected artifacts; superseding decisions link back. Deliberation in A4. |
| RM10 provenance (Partial) | — | **Linkage-discipline convention** (B3): every commit names its issue; every PR uses `Closes #`; every issue names its RQ and milestone; releases inherit the chain. |

These four conventions are what a plain GitHub repository lacks and what this architecture contributes.

## 5. Lifecycle model

`lifecycle_model.csv` maps each of 12 stages to the components active in it, its primary artifacts, and the link that carries traceability into the next stage.

```
idea ──► question ──► planning ──► literature ──► methods ──► data ──►
analysis ──► results ──► manuscript ──► publication ──► outputs ──► post-project

active components shift A4→A3→A1 (coordination) then B*/C* (record+production)
then D* (release); B3 Linkage Discipline and B4 Change History are active throughout.
```

Traceability path realised end to end:

```
RQ issue (A3)
  └─ referenced by method issue (A2) ─ in milestone (A1)
       └─ branch + commits (B4) ─ "refs #"
            └─ analysis PR (C2) ─ "Closes #", CI run (C3)
                 └─ result artifact (C1)
                      └─ manuscript section PR (C2)
                           └─ Release vX.Y (D1) ─ autogenerated notes
                                └─ Zenodo DOI (D2)
```

Any node in this chain can be reached from any other via the recorded cross-references — the operational meaning of RM10 under this architecture.

## 6. Workflow definitions

`workflows.csv` — 7 workflows, each a concrete step sequence with its trigger, components, requirements and the traceability link it creates:

| ID | Workflow | Creates |
|---|---|---|
| WF1 | Register a research question | RQ issue as the root node cited downstream |
| WF2 | Execute a research task | question → task → branch → commits → PR → merge chain |
| WF3 | Record a decision | decision issue + `Dn` entry linked to affected artifacts |
| WF4 | Peer-review an artifact | reviewer, comments, approval and checks on the PR |
| WF5 | Release and archive a research version | release tied to a commit and to all PRs since the last tag; external DOI |
| WF6 | Reproducibility check | machine-checked reproduction evidence attached to the commit |
| WF7 | Onboard / hand over | project state reconstructable from documentation alone |

## 7. What stays outside GitHub

From the Phase 5 external-tool dependencies:

| Concern | External system | Linked from |
|---|---|---|
| Large datasets | data repository (institutional, domain, Zenodo) | C1, referenced in READMEs and issues |
| Computational environment | containers (Docker/conda), lockfiles | C3 workflow, `/docs` methodology |
| DOI + preservation | Zenodo / DataCite | D2 (webhook) |
| Institutional governance, funding, workforce | the institution | D3 (documented, not solved) |

The architecture's job at these boundaries is to hold a durable, versioned **reference** (URL, DOI, identifier) inside the repository, not the artifact itself.

## 8. Implementation principles

1. **Coordination and traceability layer, not container.** Anything too large or too specialised stays external and is linked.
2. **Traceability is a discipline.** B3 is mandatory; the conventions in §4 are part of the architecture, not optional polish.
3. **Minimal viable configuration first.** Start with A1, A2, A3, B1, B2, C1; add C2, C3, D1, D2, D3 as the project matures.
4. **Prefer native over convention.** Use a convention only where Phase 5 scored Partial or Limited.
5. **Discipline-independent core.** The layout, workflows and linkage rules are generic; labels, Project fields and Issue Types are the adaptation points.
6. **Private during the work, public at publication** — an explicit governance decision (D3), after which X1 emerges.
7. **Everything regenerable.** Tables and figures come from scripts over versioned data (`analysis/`).

## 9. How the architecture realises the Phase 5 scores

- The 7 **Direct** requirements are served by native components with no added convention (A2, B1, B4, C2, C3, D1, X1).
- The 6 **Partial** requirements are served by a native component **plus** a named convention (A1, A3+B3, B2, C1, B3+B4, C2+C3, D1+D2).
- The 2 **Limited** requirements: RM2 is raised toward Partial by A3+B3 in practice; RM15's in-scope part (access, contribution rules, exit plan) is handled by D3, the rest is explicitly external.
